Ternary-Bonsai-2-27B-Uncensored-Heretic (PQ2_0) - portable llama.cpp server
===========================================================================

ЗАПУСК
------
Двойной клик по ярлыку:

    Bonsai PQ2_0 - ctx 32768.lnk      32k    KV в VRAM, f16  (самый быстрый)
    Bonsai PQ2_0 - ctx 65536.lnk      64k    KV в VRAM, f16  <- по умолчанию
    Bonsai PQ2_0 - ctx 98304.lnk      96k    KV в ОЗУ, q8_0
    Bonsai PQ2_0 - ctx 131072.lnk    128k    KV в ОЗУ, q8_0
    Bonsai PQ2_0 - ctx 196608.lnk    192k    KV в ОЗУ, q8_0
    Bonsai PQ2_0 - ctx 262144.lnk    256k    KV в ОЗУ, q8_0

Все шесть проверены: стартуют и отвечают. 32k-64k работают быстрее
всего (KV-кэш целиком в видеокарте). От 96k KV-кэш вынесен в ОЗУ.

Ждать 6-20 секунд, пока в окне не появится:
    model loaded
    listening on http://127.0.0.1:18098

Подключение клиента (OpenAI-совместимый API):
    Base URL : http://127.0.0.1:18098/v1
    API key  : любой текст или пусто
    Model    : любой текст (например "local")

Остановка: закрыть окно или Ctrl+C.

НАСТРОЙКИ (переменные окружения, задаются в ctx-*.bat)
-------------------------------------------------------
    CTX        контекст, токенов. Максимум модели 262144
    THREADS    потоков CPU, по умолчанию 12 ( Ryzen 5 5500 = 6 ядер / 12 потоков )
    PARALLEL   параллельных слотов, по умолчанию 1
    PORT       порт сервера, по умолчанию 18098

Разово из командной строки:
    set CTX=131072
    call run-server.bat
или готовый файл контекста:
    call ctx-131072.bat

Дополнительные аргументы llama-server пробрасываются как есть:
    call run-server.bat --mmproj "%~dp0mmproj-BF16.gguf"

Картинки (мультимодальность): добавь --mmproj "%~dp0mmproj-BF16.gguf"
и учти, что картинки съедают контекст.


ПОЧЕМУ ИМЕННО ТАКИЕ ФЛАГИ (проверено A/B)
-----------------------------------------
    -ngl 99    обязателен. Без него llama.cpp переносит часть слоев в RAM,
               теряется 4-5x скорости decode (23.5 против 4.2 tok/s).
    -t 12      все логические процессоры, +11.8 tok/s к -t 6.
    -np 1      один слот. Ключевая настройка: контекст делится между
               слотами, поэтому при -np 4 на ctx 65536 слот получает
               16k и decode падает с 23.1 до 10.5 tok/s.
    -fa on     flash attention, обязателен для гибридной архитектуры
               модели (линейное внимание + полное внимание).

Всё, что выше 65536, - ловушка. Подробности в следующем разделе.


ПРОВЕРКА, ЧТО КОНТЕКСТ РЕАЛЬНЫЙ
-------------------------------
Сколько токенов в окне (n_ctx) говорит только о размере выделения, но
ничего не говорит о том, что модель может этим окном пользоваться.

    GET http://127.0.0.1:18098/props   ->  default_generation_settings.n_ctx

Настоящая проверка - "игла в стоге сена": уникальный код прячется в
середине длинного промпта, вопрос задаётся в конце.

    powershell -ExecutionPolicy Bypass -File verify-context.ps1 -TargetTokens 60000

Замеры после перезагрузки, тот же промпт, -ngl 99, -t 12, -np 1:

      ctx | KV | промпт | результат | время
    32768 | VRAM |  27492 |   PASS     | 133 с   206 tok/s
    65536 | VRAM |  27492 |   PASS     | 133 с   206 tok/s
    65536 | VRAM |  60517 |   PASS     | 450 с   134 tok/s
    98304 | VRAM |  27492 | ТАЙМАУТ    | >900 с  30 tok/s
    98304 | VRAM |  87949 | ТАЙМАУТ    | >1500 с 58 tok/s
   262144 | VRAM |  27492 | ТАЙМАУТ    | >1500 с 18 tok/s

До 65536 KV-кэш помещается в 12 GB VRAM. Выше - нет, и обработка
встаёт колом. Причем важно именно значение -c, а не длина промпта:
при ctx=98304 даже 27k токенов не проходят, хотя при ctx=65536 такой
же промпт идёт 133 секунды.


КАК СДЕЛАТЬ 256k РАБОЧИМ
------------------------
Выносим KV-кэш из VRAM в ОЗУ, оставляя все 65 слоёв в видеокарте:

    -ngl 99 -nkvo -ctk q8_0 -ctv q8_0

Так веса модели (6.5 GB) остаются в VRAM, а KV-кэш (8.7 GB) идёт в RAM.
При 32 GB ОЗУ это помещается. Именно так настроен ярлык на 262144.

Проверено: промпт в 27k токенов обрабатывается за 198 с (138 tok/s),
тогда как без -nkvo тот же промпт таймаутился за 1500 с.

Но есть условие: контекст должен расти постепенно, а не за один раз.
Холодный промпт на 200k токенов не прошёл за 90 минут. Работает
инкрементальный режим - длинный диалог, где каждый ход добавляет
несколько тысяч токенов:

    47 334 токена холодным запросом       461 с
    +800 токенов с повторным запросом      23 с   (95% экономия)
    тот же запрос повторно                  7 с   (полный кэш)

Сборка 148k токенов по частям и проверка иглы на глубине 50%:

    шаг 1   22k токенов   184 с
    шаг 2   47k токенов   337 с
    шаг 3   71k токенов   559 с
    шаг 4   93k токенов   648 с
    шаг 5  118k токенов   896 с
    шаг 6  143k токенов  1050 с
    шаг 7  148k токенов   280 с
    финал  148k токенов   235 с   <- кэш, код найден  PASS

Итог: 256k контекст работает, но только в режиме длинного диалога,
а не одним большим промптом. При росте по частям каждый следующий ход
платит только за новые токены.


ОСОБЕННОСТЬ ЖЕЛЕЗА: ПОСЛЕ ДОЛГОЙ РАБОТЫ ПАДАЕТ СКОРОСТЬ
-------------------------------------------------------
После многочасовых прогонов decode падал с 23.7 до 4.0 tok/s при
идентичной команде запуска. При этом VRAM распределен верно (10.66 из
11.21 GB), утечки в системную память нет, GPU загружен на 129-159%,
CPU простаивает. Помогает перезагрузка компьютера, не перезапуск
сервера. Если скорость упала в разы - проверь это состояние, прежде
чем искать причину в настройках.


ПАРАМЕТРЫ ГЕНЕРАЦИИ
-------------------
    thinking  : temperature=1.0  top_p=0.95  top_k=20  min_p=0.05
                reasoning_effort = xhigh (по умолчанию) / medium / low
    instruct  : temperature=0.7  top_p=0.80  top_k=20  presence_penalty=1.5
Модель по умолчанию думает (thinking). Для быстрых ответов ставь
reasoning_effort=medium, иначе ответы будут длинные и медленные.


ПОРТАТИВНОСТЬ
-------------
    - Папку можно копировать целиком, все пути в bat относительные.
    - Нужен путь без кириллицы и без пробелов (BAT плохо их переваривает).
    - .gguf и папка prism-llama должны лежать рядом с .bat.
    - Ярлыки привязаны к текущему пути, после переноса папки пересоздай их
      или запускай .bat напрямую.
    - Модель НЕ грузится в LM Studio: тип ggml 142 (PQ2_0) есть только в
      форке PrismML, в стоковом llama.cpp его нет. Обновление LM Studio
      не поможет.
