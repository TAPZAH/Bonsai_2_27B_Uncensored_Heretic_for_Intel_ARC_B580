Ternary-Bonsai-2-27B-Uncensored-Heretic (PQ2_0) - portable llama.cpp server
===========================================================================

ЗАПУСК
------
Двойной клик по ярлыку с нужным контекстом:

    Bonsai PQ2_0 - ctx 32768.lnk      32k контекст, 23.5 tok/s
    Bonsai PQ2_0 - ctx 65536.lnk      64k контекст, 23.7 tok/s   <- по умолчанию
    Bonsai PQ2_0 - ctx 98304.lnk      96k контекст, 17.8 tok/s
    Bonsai PQ2_0 - ctx 131072.lnk    128k контекст,  3.7 tok/s
    Bonsai PQ2_0 - ctx 196608.lnk    192k контекст,  4.4 tok/s
    Bonsai PQ2_0 - ctx 262144.lnk    256k контекст, 21.3 tok/s

Ждать 6-18 секунд, пока в окне не появится:
    model loaded
    listening on http://127.0.0.1:18098

Подключение клиента (OpenAI-совместимый API):
    Base URL : http://127.0.0.1:18098/v1
    API key  : любой текст или пусто
    Model    : любой текст (например "local")

Остановка: закрыть окно или Ctrl+C.


ЧТО ВНУТРИ
----------
    start-bonsai.bat        запуск по умолчанию, CTX=65536
    run-server.bat          движок, читает настройки из переменных окружения
    ctx-32768.bat ...       по одному файлу на каждый контекст
    serve.bat               запуск с выбором контекста аргументом
    Bonsai PQ2_0 - ctx N.lnk ярлыки
    prism-llama/            движок (llama.cpp форк PrismML, win-vulkan)
    Ternary-...-PQ2_0.gguf  модель, 7.2 GB
    mmproj-BF16.gguf        зрительная башня, для картинок
    context-benchmark.csv   замеры скорости по всем контекстам
    bench-context.ps1       скрипт, которым сняты замеры


НАСТРОЙКИ (переменные окружения, задаются в ctx-*.bat)
-------------------------------------------------------
    CTX        контекст, токенов. Максимум модели 262144
    THREADS    потоков CPU, по умолчанию 12 ( Ryzen 5 5500 = 6 ядер / 12 потоков )
    PARALLEL   параллельных слотов, по умолчанию 1
    PORT       порт сервера, по умолчанию 18098

Разово из командной строки:
    set CTX=131072
    call run-server.bat
или
    serve.bat 131072

Дополнительные аргументы llama-server пробрасываются как есть:
    call run-server.bat --mmproj "%~dp0mmproj-BF16.gguf"

Картинки (мультимодальность): добавь --mmproj "%~dp0mmproj-BF16.gguf"
и учти, что картинки съедают контекст.


ПОЧЕМУ ИМЕННО ТАКИЕ ФЛАГИ (проверено A/B)
-----------------------------------------
    -ngl 99    обязателен. Без него llama.cpp переносит часть слоев в RAM,
               теряется 4-5x скорости decode (23.5 против 4.2 tok/s).
    -t 12      все логические процессоры, +11.8 tok/s к -t 6.
    -np 1      один слот. Ключевая настройка: контекст делится между
               слотами, поэтому при -np 4 на ctx 65536 слот получает
               16k и decode падает с 23.1 до 10.5 tok/s.
    -fa on     flash attention, обязателен для гибридной архитектуры
               модели (линейное внимание + полное внимание).


ТАБЛИЦА СКОРОСТИ ПО КОНТЕКСТУ
------------------------------
Замеры: Ryzen 5 5500 + Intel Arc B580 (12 GB VRAM), -ngl 99, -t 12, -np 1,
KV f16, промпт 2864 токена + генерация 1200 токенов.

      ctx | decode tok/s | VRAM   | RAM    | загрузка
    32768  |     23.5     | 8.8 GB | 7.1 GB |  6 с
    65536  |     23.7     | 10.8 GB| 7.1 GB |  6 с     <- лучший выбор
    98304  |     17.8     | 10.6 GB| 9.4 GB | 10 с
   131072  |      3.7     | 10.7 GB| 11.4 GB| 10 с
   196608  |  не отработал| 10.0 GB| 15.9 GB| 18 с
   262144  | не влезает   |   -    |   -    |  ошибка

С KV-кэшем q8_0 (нужен для контекстов от 128k, вдвое меньше памяти):
   131072  |      4.5     | 10.1 GB| 10.3 GB| 14 с
   196608  |      4.4     | 10.6 GB| 10.0 GB| 10 с
   262144  |     21.3     | 10.8 GB| 12.1 GB| 10 с


ЧТО НЕОЖИДАННО В ТАБЛИЦЕ
-------------------------
1) 128k и 192k проваливаются до 3.7-4.5 tok/s, хотя 96k дает 17.8.
   Причина: KV-кэш плюс веса перестают помещаться в 12 GB VRAM, часть
   памяти уходит в системную, и каждый слой читается через PCIe.

2) 256k внезарано быстрый - 21.3 tok/s, в 5 раз быстрее 192k.
   Воспроизведено три раза подряд, это не флак. С q4_0 вместо q8_0
   скорость снова падает до 4.4, то есть важна точная раскладка буферов,
   а не сам размер контекста. Практического смысла в этом нет: держать
   сервер на 256k ради скорости бессмысленно, ради контекста - да.

3) Контекст свыше 32k сам по себе замедляет decode, даже когда влезает:
       1 038 токенов в контексте  -> 25.9 tok/s
       4 034                      -> 19.4 tok/s
       8 038                      -> 14.0 tok/s
      14 044                      ->  9.9 tok/s
   Длинный диалог сам себе отвечает медленнее.


РЕКОМЕНДАЦИЯ
------------
Рабочий режим - 32768 или 65536. Больше 96k на этом железе смысла нет:
скорость обваливается, а 256k требует квантования KV-кэша.


ПАРАМЕТРЫ ГЕНЕРАЦИИ
-------------------
    thinking  : temperature=1.0  top_p=0.95  top_k=20  min_p=0.05
                reasoning_effort = xhigh (по умолчанию) / medium / low
    instruct  : temperature=0.7  top_p=0.80  top_k=20  presence_penalty=1.5
Модель по умолчанию думает (thinking). Для быстрых ответов ставь
reasoning_effort=medium, иначе ответы будут длинные и медленные.


ПОРТАТИВНОСТЬ
-------------
    - Папку можно копировать целиком, все пути в bat относительные.
    - Нужен путь без кириллицы и без пробелов (BAT плохо их переваривает).
    - .gguf и папка prism-llama должны лежать рядом с .bat.
    - Ярлыки привязаны к текущему пути, после переноса папки пересоздай их
      или запускай .bat напрямую.
    - Модель НЕ грузится в LM Studio: тип ggml 142 (PQ2_0) есть только в
      форке PrismML, в стоковом llama.cpp его нет. Обновление LM Studio
      не поможет.
